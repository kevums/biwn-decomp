What changed and how the failure was handled

The original loader searches for sixteen consecutive 32-bit marker values. The existing restoration repair searches at two-byte intervals while retaining those 32-bit comparisons. That repair now has an explicit source form; the original longword-scan C reference remains separate.

A first size-optimized C version passed its component tests but failed the fresh adaptive game route after 26,795 frames. It executed twelve compiled loader calls, with no observed task-stack boundary violation, but never reached the merchant and produced no audio on that route. Its failure was retained. The runner's positive-release-coverage assertion was unmet because the route failed; saved emulator outputs were classified without replaying or converting that failed outcome into a pass.

Restoring only the loader entry to the original repaired body, with the same payload, heap reservation and startup, completed the adaptive route in 24,956 frames. Read-only captures then showed that the first real load returned identical CPU state and 96,350 identical payload bytes, but the C scan returned at frame 244 instead of 209. Across the first twelve captured calls, all twelve returned CPU states matched; the seven non-null copy calls had seven matching payload comparisons. This is scoped boundary evidence, not proof of every call or an isolated explanation of the entire game failure.

An optimized C scan reduced a controlled case from 63,736 to 20,474 cycles. A source-assembled scan kernel reduced it to 17,298 cycles while retaining C control flow for waiting, CD calls, copying and readiness. In the fresh matched-layout capture, the kernel's first load returned at frame 209, matching the original control. All twelve captured CPU returns and seven copied payloads matched. The tested build then completed the adaptive route; no claim is made that one timing measurement proves every integration cause.
